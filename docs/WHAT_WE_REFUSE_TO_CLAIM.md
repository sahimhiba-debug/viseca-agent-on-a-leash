# What we refuse to claim

Kept deliberately short and blunt. If a claim is not on the proven list in
`WHAT_WE_CAN_PROVE.md`, it belongs here.

| We do NOT claim | Why |
| --- | --- |
| **Exactly-once payment** | At-most-once, and only within one process. Two workers restoring the same checkpoint can each consume the same authority once. **And at-most-once held only for checkpoints this code wrote**: until it was found, dropping `consumed_at` from a snapshot made a spent authority spendable again, and dropping `revoked` made a revoked one live. Both now refuse to restore (`tests/security/test_checkpoint_absence.py`); the cross-process claim is unchanged. |
| **That we cap total spending** | No mandate expressible in the official rule format can. `scope` is `purchase` or `period`, and the spec closes the set: *"No extra rule fields are allowed."* |
| **That we enforce the account's monthly limit** | It exists in `accounts.csv` and is real. The official API exposes no account-scoped spend counter and no account endpoint, so we cannot enforce it. We display it marked **not enforced**. |
| **That the one-shot job check holds across runs** | It holds within a run. Our ledger is run-scoped; the job is mandate-scoped. Reusing one mandate in a later run does not see the earlier run's fulfilment. |
| **Cryptographic authority or tamper-proof payment** | Nothing here is signed. The payment boundary is an in-process simulation. |
| **That we secure an official payment system** | The Viseca API has no payment step. `MockPSP` is ours, clearly labelled, and no production path calls it. |
| **That we understand customer intent** | We match phrase patterns. We do NOT claim the wallet enforces the customer's intent — it enforces the compiled policy, and shows them that policy plus what it could not represent. An intent-fidelity audit found six defects here, including "CHF 250 per week" compiled as a per-ORDER ceiling and reported back to the customer as theirs. Three concepts remain inexpressible in the official vocabulary (an overall total, an end date, any quantity); all three are disclosed, none enforced. See `docs/archive/FINAL_INTENT_FIDELITY_AUDIT.md`. |
| **That the coverage check finds every lost restriction** | It detects the KINDS of restriction it knows about. A restriction of an unanticipated kind is still lost silently. "No silent weakening" is measured over 4,800 generated instructions, 95 metamorphic cases and 43 annotated paraphrases — measurement over a corpus, not a proof over a language. |
| **That the compiler's interpretations were validated by anyone else** | The paraphrase expectations were annotated by the same author who wrote the fixes. No human study was performed and none is reported. |
| **That we detect merchant lies** | Item size, return windows and finality are the merchant's claims, derived from text we cannot verify. |
| **Standards compliance** | No SEPA, AP2, ACP or card-scheme certification. |
| **Novelty for one-shot mandates** | SEPA one-off mandates, card-on-file and Google AP2 Intent Mandates are prior art. |
| **That our adversarial suites are exhaustive** | 133 corpus cases, 17 matrix attacks and 9 demonstrations are a sample, not a proof. **One of the nine is not stopped**, on purpose and with the argument attached. |
| **Order independence** | The approved *set* depends on arrival order. Greedy first-come-first-served admission: 300 orderings of SCEN0001 produce 14 distinct approved sets. Safety is unaffected; allocation is not guaranteed. |
| **Fairness** | No allocation policy is enforced, deliberately. The customer stated a bound, not a preference between competing purchases. |
| **Cross-run period enforcement** | The rolling cap is enforced per RUN, matching the platform's own scope — `technical_details.md`: *"context | Spend and recent authorization information from this run"*. Measured: SCEN0001 approves CHF 387.50 per run, so ten runs put CHF 3,875 through a stated CHF 300/7-day cap. We now DISCLOSE this at confirmation. We do not enforce it. **Correction (deep-weakness campaign):** this was previously justified as a *protocol limit*, and that was overstated. No endpoint returns a **pre-aggregated** spend figure, but `POST /v1/team/reset` is documented to clear *"your team's mandates, runs, decisions, and event"* state, so the platform holds decisions **team-scoped, spanning runs**, and `GET /v1/authorizations` and `GET /v1/events?since=0` expose them. Our own `reconcile_run` says the listing *"isn't documented well enough to trust a reconstructed amount/timestamp"* — a **choice under uncertainty**, not an impossibility. The accurate statement is: an authoritative cross-run record plausibly exists, its shape is under-documented, we cannot verify it offline, and we chose not to rely on it. A cross-session ledger was built and attacked (`research/mandate_ledger_prototype.py`) — two concurrent sessions both approved against the same remaining budget and the losing write vanished, and a missing ledger file is indistinguishable from a mandate that has never spent. Claiming a bound we cannot hold would be worse than naming the one we do. |
| **That a rolling limit survives a lost checkpoint** | It survives as an UNKNOWN, not as a number. **This entry used to say the absence could not be filled and was made loud instead — that was wrong, and expensively so.** Measured: a CHF 300 / 7-day cap approved **CHF 900 inside one window across three restarts**, bounded per restart rather than per window, with a log line as the only mitigation. The reasoning that failed was the assumption that a genuinely new run and a run whose state was lost are indistinguishable. They are not: a new run has no decision recorded anywhere, and a lost one has its earlier decisions in the `GET /v1/authorizations` listing this worker **already calls** one method down. The amount still cannot be rebuilt — but "I cannot see what was spent" can be represented, and now is: rolling rules evaluate `unknown` and follow the customer's own `uncertainty_policy`. What we still do NOT claim is a reconstructed figure, or that the unknown is free: it costs an ASK, and it expires only once the state has watched a full window. |
| **Formal proof of temporal safety** | Established empirically — 12,000 monotonicity baskets, 3,000 lifecycle traces, 4,000 optimizer strategies, exhaustive small permutations. No proof was constructed. |
| **A complete evidence audit** | Thirteen absent/inapplicable/conflicting cases across the rules that exist today. A new rule field could reintroduce the same inversion. |
| **Protection against merchant lies** | `order.return_window_days` and `item.size` have no input other than merchant free text. A plausible claim ("returns accepted within 90 days") beats every realistic threshold with zero knowledge of the policy. |
| **Full schema re-validation** | We validate what this engine actually reads, not the whole schema. `_unreadable_event` refuses an event missing any field the engine dereferences, any field present but EMPTY, or a currency outside the four the FX table carries — the official worker outline makes this ours ("validate its data event"), and before it existed 1,916 of 8,124 single-field erasures made the engine RAISE rather than answer. We do not check types, ranges, formats, `minItems`, or anything the engine never reads, so a structurally invalid event that happens to carry every field we touch is still accepted and judged. The testable property is unchanged: erasing a required field never buys a more permissive decision, and now never produces a non-answer either. |
| **What the platform does if we miss a deadline** | Unknown. `technical_details.md` gives `deadline_at` as "the real-clock deadline for the automated answer" and never says what follows a missed one. Our worker fails closed on its own side -- a malformed event is logged and no decision is submitted -- but whether platform-side silence denies or approves is not documented and we have not observed it. If it approves, "submit nothing" is the wrong failure mode and this is the first thing to change. |
| **Production readiness** | In-memory state, one process, no auth on the demo API, no multi-tenancy. |
| **That a basket the agent proposes describes a real purchase** | The agent now checks that one shop stocks everything it proposes, and refuses offers that are implausible. The **wallet** cannot check either: nothing in the official API lets it verify that a merchant sells an item, so an agent that lied about its basket would be evaluated truthfully against a false description. This is an agent-side integrity property, not a wallet guarantee, and it is worth stating plainly because the previous agent did not hold it — chosen items and chosen merchant were unrelated, and on four benchmark episodes it was approved while holding goods from a shop the customer had excluded. |
| **That the agent understands the errand** | Its objective counts *lines bought*, which is a thin proxy for "the household has what it needs". It will buy the cheapest N grocery lines. A real shopping agent would model a list; this one does not, and the objective function says so in one place where anyone can read it. |
| **That the agent's search is exhaustive** | Bounded at 5 lines, 12 offers per shop and 50 shops, because an agent that enumerates without limit is a denial-of-service against its own customer. A sufficiently adversarial catalogue can hide the best basket outside those bounds. |
| **That we benchmarked a real language model** | <!-- superseded --> SUPERSEDED: two were run, see `docs/REAL_MODEL_PLANNER.md`; what we still refuse to claim is that a model improves the planner. The text that follows records the earlier state. We did not. The real-model arm is implemented and one environment variable away (`ANTHROPIC_API_KEY=... python3 research/architecture_comparison.py`), but no key was available on this machine and none was sought: the API returns 401, the `claude` CLI's OAuth would not refresh for a subprocess, and no SDK or local model is installed. The experiment did not run, which is different from running and being inconclusive. See `docs/archive/FINAL_LLM_EXPERIMENT.md`. |
| **That the stub rows of the model comparison are real-model results** | `research/architecture_comparison.py` drives the seam with **stubs** standing in for a model's behaviours — competent, careless, hallucinating, prose-replying, unavailable, flaky. No API was called and no model was benchmarked. What it measures is the ARCHITECTURE's sensitivity to those behaviours, which is why "hybrid, careless → 8/11" is the finding and not "LLMs score 8/11". A real model would have to be measured separately. |
| **That the agent finds the acceptable shop without cost** | It has no prior over which merchants a customer has used, and must not — that fact belongs to the wallet. So it discovers an acceptable shop by being refused at an unacceptable one, at a cost of one refused purchase. Bounded, not free. |
| **That a seller cannot get past a rule by publishing nothing** | They can, and one of the nine attack demonstrations does it live. A hard rule is checked against evidence the SELLER publishes; publish a bad value and the rule FAILS, publish nothing and it is UNKNOWN, which goes to `uncertainty_policy`. The party that picks the seller is the agent. Measured: 52 of 6,864 (purchase, erasure) pairs become more permissive when described with less — 26 BLOCK→REVIEW under `ask`, 26 BLOCK→ALLOW under `approve`, **0 under `decline`**. |
| **That the silence channel can be closed for one rule and not the others** | It cannot, in this format. Over every field `rules.py` evaluates — the list read from that file's own source, so a new field fails the test rather than escaping the argument — **no rule can be made to FAIL by silence**. So `uncertainty_policy` is the only lever and it is all-or-nothing. That is a gap in the official mandate format, disclosed with a witness rather than patched around. |
| **That `decline` is a free defence** | It is not. On the official catalogue **0 of 7 grocery items publish a return window**, so "only buy what I can send back" under `decline` produces an agent that gives up after five attempts and buys nothing. The CONTROL — clothing, 4 of 7 publishing, same agent and engine — completes the errand under `decline` for CHF 30 more than under `approve`. The accurate statement is that declining is not what costs; **requiring evidence nobody publishes is**, and the wallet shows the customer that trade-off rather than choosing it for them. |
| **That the read-back finds every restriction the compiler missed** | It finds words that CHANGED NOTHING, which is what it measures. 19 of 20 ordinary lost phrasings are detected and 0 of 33 well-formed sentences fire — but restriction-flavoured remarks fire too ("Do not worry about the weather", 5 of 5), and restrictions carried by a bare noun phrase are missed entirely ("Swiss shops preferred", 5 of 5). It is rendered as a receipt, not a warning, because that is the only claim the measurement supports. |
| **That a model-based compiler was tested** | The read-back takes any compiler and demonstrably reports three different results for three different vocabularies, so nothing in it is regex-specific. That is a property of the MECHANISM. No language model was called, no model-based compiler exists in this repository, and the per-word cost of one is an estimate from the mechanism's shape rather than a measurement. |
| **That the read-back analyses any instruction** | It is quadratic — one deletion per word, each a full compile — and is bounded at 150 words. Past that it returns nothing and says so, rather than analysing part of the sentence and presenting it as complete. |
| **That a witness makes a customer decide better** | The claim that a concrete purchase is easier to answer than a rule list is the product thesis behind three panels, and it has **not been user-tested**. No human study was performed and none is reported. |
| **That the absence defects are all of them** | `docs/ABSENCE.md` names **seventeen** instances of one mistake — it said seven, then twelve, then fourteen — and the count has only ever gone up. Two of the last three were created BY the fix for an earlier one, which is the strongest available evidence that the list is not closed: a fix is a new place for the mistake to live. The sweeps behind it (8,124 erasures of the official events, 22,044 of generated ones, 6,415 restatements, 4,068 pairs, every field `rules.py` evaluates, every key `to_snapshot` writes) are each bounded by the fields they enumerate. An eighteenth boundary is more likely than not. |
| **That we detect prompt injection in general** | We detect six whitelisted SHAPES of text addressed to an automated purchasing system about authorization — impersonating a system message, claiming your limits do not apply, claiming a pre-authorisation, asking for approval without confirmation, and two more. It fires on 2 of the 56 official item lines, both genuine, and on none of the other 54. A seller who phrases an instruction outside those six shapes is not detected, and nothing here reads the imperative itself. The SECURITY property is unchanged and does not depend on detection: the text was already ineffective, because there is no code path from merchant text to a rule. |
| **That a device change means a session is compromised** | It means it *might*, which is why it returns `unknown` rather than failing. A customer moving from phone to laptop trips it once per new device; a customer returning to a device this run has already seen does not. It only reaches a mandate that asked to be paused on session anomalies, so no other customer sees it at all. |
| **That "you could order this again on Monday" is a promise the platform will keep** | It is what THIS engine would decide at that moment given the spend it currently knows about, verified by re-proposing the purchase at that instant and one minute earlier. It says nothing about the shop still stocking the item, the price holding, or a purchase the wallet has not yet seen landing in between. It is reported only when the rolling window is the sole reason for the refusal. |
| **That the agent-only familiarity split reflects a rule in the specification** | It does not. `technical_details.md` says nothing about `initiator_type` and the customer's phrase "a shop I have used before" does not resolve itself. We judged that an agent's own past purchases should not silently answer a question about the customer's history, and routed the difference to `uncertainty_policy` rather than deciding it. A reasonable team could read it the other way; what we refuse to do is read it either way *silently*. |
| **That the official replay counts are a score** | 12/9/24 is a regression boundary and it has moved three times — 19/2/24 → 18/3/24 → 17/4/24 → 12/9/24 — each time because a defect was fixed, with the reasoning recorded in the commit. There are no official expected-decision labels. A team reporting a different split is not thereby wrong. |
| **That reading all 45 decisions by hand is a repeatable process** | It found three defects that no sweep in this repository could reach, and it is exactly as reliable as the attention of whoever does it. Nothing automates it. |
