# Agentic commerce: industry research and what it means for this project

This is real research (web searches run September 2026, sources cited), not
recollection. It exists to answer one question honestly: is the architecture this
project is building a plausible, well-grounded direction, or is it reinventing
something the industry has already solved differently -- and if industry-standard
concepts exist, which of them are actually applicable inside the Viseca "Agent on a
Leash" API contract, versus describing a bigger, multi-party problem this
single-team hackathon prototype does not need to solve.

## What each initiative is actually solving

### Visa Trusted Agent Protocol / Visa Intelligent Commerce

Visa Intelligent Commerce combines tokenized payment credentials, agent identity
verification through the **Trusted Agent Protocol** (developed with Cloudflare),
and settlement infrastructure, so AI agents can "search, compare and pay on behalf
of consumers, while ensuring trust between merchants and AI agents." The protocol
targets **agent-to-merchant** communication -- proving to a merchant's storefront
that a given HTTP request genuinely comes from an authorized agent (not a bot
scraping the site), which is a different problem from "should this specific
purchase be authorized."
[Visa Introduces Trusted Agent Protocol](https://investor.visa.com/news/news-details/2025/Visa-Introduces-Trusted-Agent-Protocol-An-Ecosystem-Led-Framework-for-AI-Commerce/default.aspx),
[Enabling AI agents to buy securely](https://www.visa.com/en-us/solutions/intelligent-commerce).

### Mastercard Agent Pay / Agentic Tokens

Agentic Tokens are "dynamic, cryptographically secure credentials" that bind a
tokenized card credential to **a specific agent, a specific merchant scope, and a
specific consent policy** -- restrictable "by agent, merchant, category, spending
limit, timeframe or usage rules." This is the closest industry analog to what this
project calls a wallet policy/mandate: a narrowly scoped, revocable grant of
spending authority, expressed as a token rather than a server-side rule list.
[How Mastercard's agentic tokens are driving agentic AI commerce](https://www.mastercard.com/us/en/news-and-trends/stories/2025/agentic-commerce-momentum.html),
[Mastercard Agent Pay](https://www.mastercard.com/us/en/business/artificial-intelligence/mastercard-agent-pay.html).

### Google AP2 (Agent Payments Protocol)

The most structurally relevant precedent found. AP2 represents every
agent-initiated purchase as **three chained, cryptographically signed W3C
Verifiable Credentials**:

1. **Intent Mandate** -- signed by the user upfront, with explicit constraints:
   price cap, time window, merchant allowlist, item specification, and a
   "prompt playback" (a natural-language restatement of what the user asked for).
2. **Cart Mandate** -- generated by the merchant from the agent's proposal,
   containing the specific cart and price, and (when the human is present at
   purchase time) signed by the user's own device key.
3. **Payment Mandate** -- a narrower, network-facing derived credential
   containing amount range, allowed payee (merchant), allowed payment
   instrument, and agent-recurrence conditions -- this is what the card network
   and issuer actually see.

[AP2 specification](https://ap2-protocol.org/specification/),
[Announcing AP2 | Google Cloud Blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol),
[The Missing Trust Layer: AP2 and Verifiable Mandates](https://gohsoonheng00.medium.com/the-missing-trust-layer-a-deep-dive-into-the-agent-payments-protocol-ap2-and-verifiable-mandates-4cd2a1674316).

### OpenAI Agentic Commerce Protocol (ACP) / Delegated Payment

Co-maintained by OpenAI and Stripe. Its Delegated Payment spec issues a payment
token restricted by **max amount and expiry**, scoped so it "cannot be used
outside the defined limits of the user-approved purchase" -- settlement, refunds,
and compliance stay with the merchant/PSP. Narrower in scope than AP2 (one
token, not a three-mandate chain), but the same core idea: derive a
tightly-bounded, single-purpose credential from a broader approval.
[Delegated Payment Spec](https://developers.openai.com/commerce/specs/payment),
[ACP GitHub](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol).

### FIDO Alliance's new Agentic Authentication and Payments working groups

Announced 2026: two technical working groups, one on **verifiable user
instructions and agent authentication** (chaired by CVS Health/Google/OpenAI, with
Amazon/Google/Okta as vice-chairs), one on **agent-initiated commerce specs**
(chaired by Mastercard and Visa), building on initial contributions from AP2 and
Mastercard's Verifiable Intent. Three focus areas: verifiable user instructions,
agent authentication, and trusted delegation for commerce.
[FIDO Alliance to Develop Standards for Trusted AI Agent Interactions](https://fidoalliance.org/fido-alliance-to-develop-standards-for-trusted-ai-agent-interactions/),
[Google and Mastercard contribute standards to FIDO](https://www.pymnts.com/news/artificial-intelligence/2026/google-and-mastercard-contribute-agentic-commerce-standards-to-fido-alliance/).

### EMVCo's draft "Agentic Payments -- Framework for Specifications" (September 2026)

Published for public comment through September 30, 2026 (i.e., during this
challenge's own timeframe). Introduces **"Intent Services"**: a shared,
interoperable layer letting multiple payment ecosystem participants "register,
reference, retrieve and manage consumer-authorised intent" across the *entire*
transaction lifecycle, not just within one issuer's own system.
[EMVCo Proposes Intent Layer for Agentic Card Payments](https://www.pymnts.com/news/artificial-intelligence/2026/emvco-proposes-intent-layer-for-agentic-card-payments),
[How EMVCo is Working to Enable Secure, Interoperable Card-Based Agentic Payments](https://www.emvco.com/knowledge-hub/how-emvco-is-working-to-enable-secure-interoperable-and-scalable-card-based-agentic-payments/).

## What is authenticated, what is delegated, and how revocation works, across these systems

| System | What's authenticated | What's delegated | Authorization representation | Revocation |
| --- | --- | --- | --- | --- |
| Visa TAP | The agent's identity to the merchant (via Cloudflare-assisted signals) | Nothing payment-specific -- this is a communication-trust layer | N/A (complementary to VIC's tokens) | N/A |
| Mastercard Agent Pay | The agent, via Agentic Tokens bound to MDES | Spend, scoped by agent+merchant+category+limit+timeframe | A token (server-side scoped credential) | Token revocation/expiry |
| Google AP2 | The user (device key signs Intent/Cart Mandates); the merchant (signs Cart Mandate) | Spend, scoped by the Intent Mandate's constraints, narrowed further in the Payment Mandate | Three chained W3C Verifiable Credentials, cryptographically signed | Mandate expiry (TTL) is designed in from the start; explicit revocation is less emphasized in what was found |
| OpenAI ACP | The user (via the platform's own auth); the PSP issues the token | A single-purpose payment token, amount+expiry bound | A restricted payment token | Token expiry; single-use by construction |
| FIDO WGs | Working towards phishing-resistant user->agent authorization and agent->service authentication | Not yet specified (in-progress standards work) | Not yet finalized | Not yet finalized |
| EMVCo draft | Multi-party "intent" records, registered and retrievable across the ecosystem | Consumer-authorized intent, tracked through its lifecycle across participants | "Intent Services" registry entries | Lifecycle state management (draft framework, comment period open) |

## What is genuinely applicable inside the Viseca API contract, and what is not

The Viseca challenge's own API is deliberately simpler than any of the above: one
customer, one mandate (not three chained ones), a flat `hard_rules` list, and
`approve`/`decline`/`step_up` as the only wire vocabulary -- there is no
cryptographic signing, no agent identity field, no merchant-facing protocol, and
no multi-party intent registry in the official schema. Building any of TAP,
Agentic Tokens, AP2, ACP, FIDO's forthcoming specs, or EMVCo's Intent Services
literally would mean inventing fields the official API does not have and cannot
verify -- a direct violation of this project's own "preserve compatibility with
the official API lifecycle" rule, and also simply infeasible without a real card
network, a real merchant PKI, or a real FIDO relying party, none of which this
challenge provides or asks for.

What IS applicable, adapted rather than copied:

- **The core idea of a narrow, derived, single-purpose payment authority** (AP2's
  Payment Mandate; OpenAI's restricted payment token; Mastercard's Agentic
  Token) -- this project already has the *ingredients* (`StoredDecision`'s
  merchant/basket/amount fingerprint, `MockPSP`'s independent re-gating) but not
  a single, explicit, inspectable object representing them. See
  `docs/archive/RND_CAPABILITY_AUTHORITY.md`.
- **AP2's "prompt playback" concept** (restating the user's own intent back to
  them in plain language before they sign off) is directly analogous to what this
  project's `policy_compiler.py` already does via `guidance`/`open_questions` --
  worth strengthening, not inventing from scratch. See `docs/archive/RND_POLICY_SIMULATOR.md`.
- **The Intent/Cart/Payment three-tier separation's underlying principle**
  ("what the user asked for" vs. "what the agent assembled" vs. "what actually
  gets charged" are three different things that can legitimately diverge) is
  directly relevant to this challenge's own "manipulated agent" scenario theme --
  adapted as a local **authorization drift** analysis, not as a second and third
  mandate type the official API does not support. See `docs/archive/RND_AUTHORIZATION_DRIFT.md`.
- **Agent identity verification (TAP, Agentic Tokens' per-agent binding, FIDO's
  agent authentication work)** is explicitly **not applicable**: the official
  Viseca schema has no agent identity field at all (`authorization.initiator_type`
  is always the literal string `"agent"`, with no further identifier), and
  inventing one would not be verifiable against anything the platform actually
  checks. Recorded as a rejected direction in `docs/archive/RND_AGENT_IDENTITY.md`.
- **EMVCo's multi-party Intent Services registry** is explicitly **not
  applicable**: it solves a problem (intent visible and retrievable across
  competing payment ecosystem participants) this single-team, single-issuer
  hackathon sandbox does not have.

| Multi-party intent registry | EMVCo draft | -- | -- | Yes -- solves a multi-issuer problem this single-sandbox challenge doesn't have |
